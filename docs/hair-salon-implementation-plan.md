## 3. 各阶段明细

### P1 会员资产闭环 🔴

**需求章节**：9.3 会员等级 / 9.4 会员余额 / 9.5 余额流水 / 9.6 积分 / 9.7 标签 / 9.8 备注

**功能点**：
- [ ] 会员等级配置（影响折扣、积分倍率、充值优惠、权益）
- [ ] 会员余额：本金余额 / 赠送余额 / 可用总余额 / 冻结金额，分开展示
- [ ] 会员余额流水：充值、充值赠送、消费扣款、退款退回、手工调整、转入转出；记录变动前/变动额/变动后/业务类型/关联订单/操作人/时间/备注
- [ ] 会员积分及积分流水：消费/充值/活动/手工来源；抵扣/兑换/扣减/过期消耗
- [ ] 会员标签（高价值/烫染/流失风险/新会员/老客户/生日等）
- [ ] 会员备注扩展（发质/偏好发型/常用发型师/过敏/禁忌）

**预估表**：`salon_member_level`、`salon_member_balance`（或字段下沉到 member）、`salon_member_balance_log`、`salon_member_point_log`、`salon_member_tag`、`salon_member_tag_rel`

**关键决策（见 §5 待确认）**：消费扣款优先扣本金还是赠送；赠送余额是否计提成。

**验收**：26.2 会员验收。

### P2 服务项目与商品主数据 🔴

**需求章节**：11 服务项目 / 12 商品管理

**功能点**：
- [ ] 项目分类维护（剪发/烫发/染发/护理/洗护/造型）
- [ ] 服务项目：名称、分类、标准价、会员价、服务时长、启用、是否参与折扣、是否计算提成
- [ ] 服务人员绑定规则（主服务人员 + 助理，影响业绩提成）
- [ ] 商品分类维护
- [ ] 商品信息：名称、分类、条码、销售价、成本价、库存数量、启用、是否参与折扣、是否计算提成
- [ ] 商品销售规则：改数量、改单价、折扣、绑销售人员（落地在 P5 订单侧）

**预估表**：`salon_service_category`、`salon_service`、`salon_goods_category`、`salon_goods`

**验收**：服务/商品可维护并在订单（P5）中可选。

### P3 卡项管理 🟡

**需求章节**：10 卡项管理

**功能点**：
- [ ] 次卡（卡名、可用项目、总次数、剩余次数、有效期、适用门店、使用记录）
- [ ] 套餐卡（含服务 + 商品、售价、有效期、使用次数、使用规则）
- [ ] 折扣卡（折扣比例、适用服务/商品、有效期、是否可叠加券）— 可缓
- [ ] 卡项核销：校验有效性 / 适用性、扣减次数或权益、生成核销记录、关联订单
- [ ] 会员持卡档案与使用记录

**预估表**：`salon_card`（卡模板）、`salon_member_card`（会员持有）、`salon_card_consume_log`（核销记录）

**依赖**：P1（会员）、P2（服务/商品，卡内含项目）

**验收**：10.4 卡项核销；卡项可在订单（P5）中作为支付/核销方式。

### P4 会员充值 🔴

**需求章节**：15 充值

**功能点**：
- [ ] 会员充值：会员、充值金额、赠送金额、支付方式、充值门店、操作人、时间、备注
- [ ] 充值活动配置（充 500 送 50 等）：名称、生效/失效时间、适用门店、门槛、赠送、启用
- [ ] 充值财务规则：本金计预收款（不计营业收入）；赠送单独记录，不与本金混淆
- [ ] 充值产生余额流水（本金/赠送分流水）

**预估表**：`salon_recharge_order`、`salon_recharge_activity`

**依赖**：P1（会员余额 + 流水）

**关键决策（见 §5）**：充值活动是否叠加优惠券。

**验收**：26.2 余额正确增加 + 每次变动有流水；26.5 充值不计营业收入。

### P5 收银开单（核心）🔴

**需求章节**：13 收银订单

**功能点**：
- [ ] 开单：散客 / 会员；服务项目 + 商品；服务人员 + 销售人员；优惠；支付方式；备注
- [ ] 挂单 / 取单 / 取消挂单
- [ ] 订单金额：原价、折扣、优惠券、积分抵扣、应收、实收、找零
- [ ] 支付方式：现金/微信/支付宝/银行卡/会员余额/赠送余额/优惠券/积分抵扣/其他
- [ ] 组合支付（一笔订单多种支付方式）
- [ ] 会员余额支付（扣减本金/赠送，按 P1 决策的扣减顺序）
- [ ] 卡项核销支付（联动 P3）
- [ ] 订单状态机：待支付 / 已支付 / 已取消 / 部分退款 / 已退款
- [ ] 小票打印（门店名、单号、时间、明细、支付方式、优惠、实收、余额、操作员）

**预估表**：`salon_order`、`salon_order_item`（服务/商品明细 + 服务人员绑定）、`salon_order_payment`（支付明细，支持组合支付）、`salon_order_card_consume`（卡项核销明细）

**依赖**：P1、P2、P3、P4

**关键决策（见 §5）**：赠送余额消费是否计提成；多发型师同单业绩分摊；提成按原价/折后/实收。

**验收**：26.3 收银验收。

## 5. 开发前待确认问题（影响建模，需求 28.1 / 28.2）

> 这些问题直接决定 P1/P5/P7 的数据模型与计算口径，建议进入对应阶段前先拍板。

### 5.1 业务规则（28.1）
- [ ] 会员是否全租户通用？（单店期等价，影响多店扩展建模）
- [ ] 消费扣款优先扣本金还是赠送金额？**→ 影响 P1 余额扣减、P6 退款退回**
- [ ] 退款时本金和赠送金额如何退回？**→ 影响 P6**
- [ ] 赠送余额消费是否计入员工提成？**→ 影响 P7**
- [ ] 不同发型师参与同一订单时业绩如何分摊？**→ 影响 P5 服务人员绑定、P7**
- [ ] 发型师提成按原价 / 折后价 / 实收金额计算？**→ 影响 P7**
- [ ] 充值活动是否支持叠加优惠券？**→ 影响 P4**
- [ ] 会员卡项是否允许转赠？**→ 影响 P3**
- [ ] 门店是否需要交班功能？**→ 影响 P8（日结 vs 交班）**
- [ ] 是否接入微信/支付宝官方支付？**→ 影响 P5 支付方式落地深度**

### 5.2 客制化与小程序（28.2）

## 6. 跨阶段公共事项

每个阶段落地时需同步处理，避免遗漏：

| 事项 | 说明 |
|------|------|
| **租户隔离** | 业务表继承 `BaseTenantEntity`，查询/导出/报表强制带租户条件（需求 6.4、27.2） |
| **门店数据权限** | 走 `salon_store_user` + `SalonStorePermissionService`，复用现有机制 |
| **权限种子** | 新接口同步 `perm`（`biz:xxx:动作`）种子；`sql.init.mode=never`，存量库手工跑 SQL |
| **`@PreAuthorize`** | 每个对外 HTTP 方法必备；仅登录 `isAuthenticated()`，按钮级走 perm |
| **模型字段说明** | Entity 字段 `/** */` Javadoc；Form/Query/VO 字段 `@Schema`；含义与 SQL COMMENT 一致 |
| **建表注释** | PG 用 `COMMENT ON TABLE/COLUMN`；schema.sql 带注释，存量库用 `sql/migrate-*.sql` |
| **字典** | 业务只存 value；VO `@Dict` + Controller `@QueryDict`，勿手写拼装 |
| **编号规则** | 业务单号统一走 P10 编号规则服务，勿散落各处硬编码 |
| **可追溯** | 订单/支付/退款/充值/余额变动/卡项核销/提成/日结 必须可追溯（需求 24.4） |
| **防重复提交** | 收银、充值、退款等写接口按需 `@PreventDuplicateResubmit`（需求 24.2） |

## 7. 推进建议

1. **先拍板 §5 待确认问题**，尤其是余额扣减顺序与提成口径——它们影响 P1/P5/P6/P7 的表结构与计算逻辑，后置返工成本高。
2. **按 P1 → P2 → P4 → P3 → P5 → P6 → P8 → P7 → P9 顺序推进**：先打通"会员资产 + 主数据 + 充值"，再收银，再退款，再日结，最后业绩与报表。P3 卡项可在 P5 之前做，也可先做最小核销在 P5 内联调。
3. **P5 收银是最大风险点**（组合支付 + 余额 + 卡项 + 状态机 + 小票），建议单独拆子任务并充分测试。
4. **P11 品牌客制化可与任意阶段并行**，不阻塞核心闭环，建议靠前穿插以验证"配置而非改代码"边界。
