# 理发店 SaaS 管理平台需求文档

## 1. 文档说明

### 1.1 文档目的

本文档用于梳理理发店 SaaS 管理平台的产品需求，明确系统建设目标、用户角色、业务范围、功能模块、核心业务规则和验收标准，为后续原型设计、接口设计、数据库设计、开发排期和测试验收提供依据。

### 1.2 产品定位

本系统面向独立理发店、美发店、造型工作室（首期以**单店商户**为主），提供集收银、会员、预约、员工、库存、财务、营销、报表于一体的门店经营管理平台。

系统以 **SaaS 多租户** 方式提供服务：

- **后端统一复用**：一套业务后端服务，所有商户共用同一套能力与接口
- **数据按租户隔离**：不同理发店之间会员、订单、财务等数据互不可见
- **前端可客制化**：各商户可有独立的店名、品牌展示、主题与小程序外观配置

平台方可统一管理商户、套餐、订阅、功能权限和运营数据。首期**不把连锁多门店**作为主场景，后续再扩展。

### 1.3 首期建设原则

| 原则 | 说明 |
|------|------|
| 一店一租户 | 前期每个独立理发店对应一个租户，用 `tenant_id` 区分，不出现跨店连锁数据问题 |
| 后端复用 | 业务逻辑、接口、数据模型统一；通过租户配置开关能力，而不是为每个店单独开发后端 |
| 前端可配置 | 店名、Logo、主题色、小程序名称与分享文案等走租户品牌配置，避免硬编码 |
| 先单店后连锁 | 首期不做集团/连锁总部；预留门店实体，但默认一个租户一个门店 |
| 功能可套餐化 | 能力按套餐开关，便于商业化，也避免所有商户功能一刀切 |

### 1.4 文档范围

本文档只描述业务需求，不包含以下内容：

- 技术架构设计（仅描述与需求相关的产品分层原则）
- 数据库表结构设计
- 接口协议设计
- 前端页面详细交互稿
- 第三方支付具体对接方案
- 具体开发任务拆分

## 2. 项目背景

传统理发店在日常经营中常见以下问题：

- 收银依赖人工记录，订单、退款、挂账容易出错
- 会员充值、赠送、余额、次卡、套餐卡管理混乱
- 员工业绩和提成统计依赖手工核算
- 老板无法实时查看门店营业额、会员消费、库存和财务状况
- 多门店经营时，数据分散，难以统一管理
- 会员留存和营销缺少系统化工具

本系统希望通过数字化工具帮助理发店降低经营管理成本，提高收银准确性、会员复购率和财务透明度。

## 3. 建设目标

### 3.1 业务目标

- 支持门店完成日常开单、收银、退款、会员充值等核心经营动作
- 支持会员余额、赠送金额、积分、次卡、套餐卡等资产管理
- 支持老板实时查看营业、会员、员工、库存和财务数据
- 支持员工绩效、服务业绩、销售业绩和提成统计
- 支持平台方以 SaaS 模式管理多个独立商户
- 支持各商户品牌与小程序展示的基础客制化
- 支持后续扩展预约、营销、小程序会员端、连锁门店等能力

### 3.2 产品目标

- 操作简单，适合门店前台和发型师快速上手
- 收银流程稳定，减少结账、退款、对账错误
- 财务口径清晰，会员充值和实际收入分开统计
- **首期主场景：单店商户 + 平台运营**；连锁作为后续扩展
- 产品功能可按套餐开关，便于商业化售卖
- 同一套后端服务支撑多家不同品牌理发店，前端按租户呈现差异

## 4. 用户角色

### 4.1 平台管理员

平台管理员由 SaaS 服务提供方使用，负责管理所有入驻商户。

主要职责：

- 管理租户/商户
- 管理 SaaS 套餐
- 管理商户订阅状态
- 查看平台运营数据
- 配置全局系统参数
- 处理商户反馈和异常问题

### 4.2 商户老板

商户老板是理发店或连锁品牌的经营负责人。

主要职责：

- 查看门店经营数据
- 管理门店、员工和权限
- 管理会员、商品、服务项目
- 查看财务报表和员工业绩
- 配置提成、营销和业务规则

### 4.3 店长

店长负责单个门店的日常运营管理。

主要职责：

- 管理本门店员工
- 查看本门店营业数据
- 处理订单、退款、会员、库存
- 管理排班和预约
- 进行日结和交班

### 4.4 收银员

收银员负责前台接待、开单和结账。

主要职责：

- 新建订单
- 添加服务、商品、会员
- 收款、挂单、撤单、退款
- 办理会员充值
- 打印小票

### 4.5 发型师/技师

发型师或技师负责服务顾客。

主要职责：

- 查看自己的预约和服务订单
- 绑定服务项目业绩
- 查看个人业绩和提成
- 记录服务备注

### 4.6 财务人员

财务人员负责收入、支出、对账和结算。

主要职责：

- 查看营业收入
- 查看会员充值和消费核销
- 查看支付渠道汇总
- 查看退款记录
- 查看员工提成
- 导出财务报表

### 4.7 会员/顾客

会员或顾客可通过门店前台、小程序或其他入口参与服务。

主要职责：

- 查询会员余额、积分、卡项
- 预约服务
- 查看消费记录
- 领取优惠券
- 接收门店通知

## 5. 业务范围

### 5.1 当前核心范围

首期系统应重点覆盖以下业务：

- SaaS 租户管理
- 门店管理
- 员工与权限管理
- 会员管理
- 会员充值与余额管理
- 服务项目管理
- 商品管理
- 收银开单
- 支付记录
- 退款管理
- 员工业绩统计
- 基础财务报表
- 日结和营业统计

### 5.2 后续扩展范围

后续可逐步扩展以下能力：

- 在线预约
- 小程序会员端
- 库存管理
- 员工排班
- 优惠券和营销活动
- 短信/微信通知
- 连锁门店管理
- 商品进销存
- 高级经营分析
- 第三方支付自动对账

### 5.3 暂不纳入范围

以下内容暂不作为首期重点：

- 复杂 ERP 财务核算
- 工资自动发放
- 大型连锁集团财务合并
- 供应商采购协同
- 门店摄像头、闸机等硬件集成
- 自研即时通讯系统

## 6. SaaS 租户与多店隔离需求

### 6.1 租户定义

租户代表一个**独立商户**（一家理发店或一个品牌主体）。每个租户拥有独立的数据、员工、会员、订单、财务和业务配置。

**首期约定：**

- 默认 **1 租户 = 1 门店**
- 不同理发店之间通过租户 ID 完全隔离，不会出现业务上的“连锁数据串通”
- 系统内部仍保留门店实体，便于以后同一租户扩展多门店，但首期 UI 与权限可按单店简化

### 6.2 租户创建

平台管理员可创建租户，并填写以下信息：

- 商户名称（对内管理用）
- 联系人姓名
- 联系电话
- 所属行业
- 商户状态
- 开通套餐
- 开通时间
- 到期时间
- 最大门店数量（首期默认 1）
- 最大员工数量

创建租户时，系统应同步初始化：

- 默认门店（与商户同名或可编辑）
- 老板账号
- 默认角色与权限
- 默认品牌配置（见 6.7）
- 默认业务基础配置（支付方式、编号规则等）

### 6.3 租户状态

租户应至少包含以下状态：

- 待启用
- 正常
- 已过期
- 已停用
- 已注销

### 6.4 租户隔离（底线）

系统应保证：

- 不同租户之间的会员、订单、财务、库存、员工数据不可互相查看
- 所有业务查询、导出、报表必须强制带租户条件
- 平台管理员可按权限查看租户数据
- 商户侧账号只能访问所属租户数据
- 小程序端按租户识别当前门店，不可跨租户访问他人会员资产

**说明：** 前期即使有多个不同理发店使用同一套系统，只要严格按租户隔离，就不会出现“连锁式”数据混用问题。

### 6.5 套餐与功能限制

平台应支持配置不同 SaaS 套餐，例如：

- 基础版（单店收银 + 会员）
- 专业版（+ 预约、营销、报表）
- 连锁版（后续：多门店汇总与总部能力）

套餐可限制：

- 门店数量
- 员工数量
- 会员数量
- 是否支持多门店
- 是否支持库存
- 是否支持营销
- 是否支持高级报表
- 是否支持小程序 / 品牌客制化

### 6.6 到期与停用规则

租户到期后，系统应支持以下策略：

- 提前提醒商户续费
- 到期后限制新增订单或新增会员
- 到期后允许查看历史数据
- 停用后禁止商户账号登录
- 平台管理员可手动恢复租户

### 6.7 租户品牌与前端客制化（核心）

多家不同理发店共用后端，但顾客与员工看到的前端应可呈现各自品牌。系统应支持按租户配置以下信息。

#### 6.7.1 基础品牌信息

| 配置项 | 用途 | 首期是否必须 |
|--------|------|--------------|
| 对外店名 / 品牌名 | 管理后台标题、小票、小程序 | 是 |
| Logo | 登录页、小程序、小票 | 是 |
| 门店电话 | 小程序联系、小票 | 是 |
| 门店地址 | 小程序展示、导航 | 是 |
| 营业时间文案 | 小程序 / 预约页 | 建议 |
| 简介 / 宣传语 | 小程序首页 | 建议 |
| 客服微信 / 二维码 | 顾客端联系 | 可选 |

#### 6.7.2 视觉与主题

| 配置项 | 说明 | 首期建议 |
|--------|------|----------|
| 主题色 / 主色 | 按钮、导航强调色 | 支持 1 套主色即可 |
| 辅助色 | 可选 | 可暂缓 |
| 登录页背景 / Banner | 管理端或小程序 | 可选 |
| 字体 / 复杂皮肤 | 高级定制 | 首期不做 |

#### 6.7.3 小程序相关客制化

若开通小程序能力，每个租户应至少可配置：

- 小程序展示名称（与微信侧审核名称策略需单独约定）
- 首页 Banner / 轮播图
- 分享标题、分享封面图
- 客服入口文案
- 关于我们 / 门店介绍
- 是否展示预约、会员卡、优惠券等模块（可与套餐联动）

**产品策略建议（写进需求即可，实现分阶段）：**

1. **方案 A（首期推荐）**：平台统一一个小程序主体，通过租户码 / 门店码 / 场景值进入对应租户；展示内容读该租户品牌配置  
2. **方案 B（后续）**：为有独立品牌诉求的商户提供独立小程序（需单独 AppID、审核与发布流程）

首期需求文档按 **方案 A** 描述，方案 B 列为扩展。

#### 6.7.4 管理后台与小票客制化

- 管理后台登录后展示当前租户店名与 Logo
- 小票抬头使用租户对外店名、电话、地址、Logo（若打印机支持）
- 系统内部仍可用统一产品名（平台名），与商户对外品牌区分

#### 6.7.5 客制化边界（避免做成项目制）

需求上明确：**客制化 = 配置，不是改代码**。

| 可配置（租户级） | 不可首期客制（保持统一） |
|------------------|--------------------------|
| 店名、Logo、主题色、文案、Banner | 业务流程（收银、充值、退款口径） |
| 小程序首页模块开关 | 核心数据模型与接口 |
| 营业时间、联系方式 | 权限模型骨架 |
| 服务项目名称与价格（业务数据本身） | 为单店定制特殊代码分支 |

若某商户需要“完全不同的页面结构 / 特殊流程”，应评估为**定制项目**或后续插件能力，不纳入标准 SaaS 首期。

### 6.8 多租户产品分层（需求视角）

从需求上把系统拆成三层，便于评审与排期：

```text
┌─────────────────────────────────────────┐
│  展示层（可客制）                          │
│  店名 / Logo / 主题 / 小程序文案与模块     │
├─────────────────────────────────────────┤
│  配置层（租户差异）                        │
│  套餐开关 / 业务规则 / 提成 / 积分 / 权限  │
├─────────────────────────────────────────┤
│  能力层（统一复用）                        │
│  会员 / 收银 / 充值 / 退款 / 报表 / 权限内核 │
└─────────────────────────────────────────┤
```

- **能力层**：所有理发店共用，保证后端复用
- **配置层**：各店规则不同，但不改代码
- **展示层**：各店看起来不一样（尤其有小程序时）

## 7. 门店管理需求

### 7.1 门店信息

系统应支持维护门店信息：

- 门店名称
- 门店编号
- 联系电话
- 门店地址
- 营业时间
- 门店状态
- 门店负责人
- 所属租户

### 7.2 门店状态

门店应至少支持以下状态：

- 正常营业
- 暂停营业
- 已关闭

### 7.3 首期单店规则

首期默认：

- 一个租户仅一个门店
- 老板 / 店长 / 收银员数据范围即本店
- 界面可隐藏“门店切换”“跨店汇总”等连锁能力
- 创建租户时自动创建默认门店，避免用户理解“租户 / 门店”两套概念

### 7.4 多门店规则（后续扩展）

当租户开通多门店能力时：

- 老板可查看所有门店数据
- 店长默认只能查看本门店数据
- 收银员默认只能操作本门店订单
- 会员可按租户统一管理，也可按业务规则限制到指定门店使用
- 报表应支持单门店查看和多门店汇总查看

## 8. 员工与权限需求

### 8.1 员工管理

系统应支持维护员工信息：

- 员工姓名
- 手机号
- 工号
- 所属门店
- 岗位
- 入职时间
- 离职时间
- 员工状态
- 是否允许登录系统

### 8.2 岗位管理

系统应支持常见岗位：

- 老板
- 店长
- 收银员
- 发型师
- 助理
- 财务
- 平台管理员

### 8.3 权限管理

系统应支持基于角色的权限控制。

权限范围应包括：

- 菜单访问权限
- 按钮操作权限
- 数据查看范围
- 财务敏感数据查看权限
- 退款审批权限
- 报表导出权限

### 8.4 员工状态

员工应至少支持以下状态：

- 在职
- 停用
- 离职

离职员工不可继续登录系统，但历史订单、业绩和提成记录应保留。

## 9. 会员管理需求

### 9.1 会员建档

系统应支持创建会员，会员信息包括：

- 姓名
- 手机号
- 性别
- 生日
- 会员等级
- 所属门店
- 推荐人
- 备注
- 标签
- 注册时间

### 9.2 会员查询

系统应支持通过以下方式查询会员：

- 手机号
- 姓名
- 会员编号
- 标签
- 会员等级

### 9.3 会员等级

系统应支持配置会员等级。

会员等级可影响：

- 服务折扣
- 商品折扣
- 积分倍率
- 充值优惠
- 专属权益

### 9.4 会员余额

会员余额应区分：

- 本金余额
- 赠送余额

系统应清晰展示：

- 当前本金余额
- 当前赠送余额
- 可用总余额
- 冻结金额
- 最近充值时间
- 最近消费时间

### 9.5 余额流水

会员余额每次变化都必须产生流水。

流水类型应包括：

- 充值
- 充值赠送
- 消费扣款
- 退款退回
- 手工调整
- 余额转入
- 余额转出

流水应记录：

- 变动前金额
- 变动金额
- 变动后金额
- 业务类型
- 关联订单
- 操作人
- 操作时间
- 备注

### 9.6 积分管理

系统应支持会员积分。

积分来源包括：

- 消费获得
- 充值获得
- 活动赠送
- 手工调整

积分消耗包括：

- 抵扣消费
- 兑换商品
- 手工扣减
- 过期清零

积分每次变化都必须记录流水。

### 9.7 会员标签

系统应支持给会员添加标签，例如：

- 高价值客户
- 烫染客户
- 流失风险
- 新会员
- 老客户
- 生日客户

- 有效期

### 10.3 折扣卡

## 14. 退款需求

### 14.1 退款类型

系统应支持：

- 整单退款
- 部分退款
- 服务退款
- 商品退款
- 会员充值退款

### 14.2 退款规则

退款时系统应校验：

- 原订单是否存在
- 原订单是否已支付
- 可退款金额是否充足
- 当前员工是否有退款权限
- 是否超过允许退款时间
- 是否需要店长或老板审批

### 14.3 退款记录

每次退款必须生成退款记录。

退款记录应包含：

- 原订单
- 退款金额
- 退款方式
- 退款原因
- 申请人
- 审批人
- 退款时间
- 退款状态

### 14.4 会员余额退款

如果订单使用会员余额支付，退款时应按规则退回会员账户，并生成余额流水。

### 14.5 退款审批

系统应支持配置退款审批规则。

例如：

- 小额退款无需审批
- 超过指定金额需要店长审批
- 会员充值退款必须老板审批

## 15. 充值需求

### 15.1 会员充值

系统应支持会员充值。

充值时应记录：

- 充值门店
- 操作人
- 充值时间
- 备注

### 15.2 充值活动

系统应支持配置充值活动。

例如：

- 充 500 送 50
- 充 1000 送 150
- 充 2000 送 400

充值活动应支持：

- 活动名称
- 生效时间
- 失效时间
- 适用门店
- 充值金额门槛
- 赠送金额
- 是否启用

### 15.3 充值财务规则

会员充值金额不直接计入营业收入。

充值本金应视为预收款。会员后续实际消费并核销余额时，系统再确认对应营业收入。

赠送金额应单独记录，不能与本金混淆。

## 26. 核心业务验收标准

### 26.1 租户验收

- 平台管理员可以创建、启用、停用租户
- 创建租户后自动初始化默认门店、老板账号与默认品牌配置
- 商户账号只能访问本租户数据
- 租户到期后系统能按规则限制使用
- 不同租户之间的数据不可互相访问
- 租户 A 的会员 / 订单 / 报表在租户 B 账号下完全不可见

### 26.2 会员验收

- 可以新增、编辑、查询会员
- 手机号重复时系统能进行提示
- 会员充值后余额正确增加
- 每次余额变化都有流水记录
- 会员消费后余额正确扣减
- 本金余额和赠送余额能分开展示

### 26.3 收银验收

- 可以创建散客订单
- 可以创建会员订单
- 订单可添加服务和商品
- 订单可绑定服务人员
- 支持现金、微信、支付宝、会员余额等支付方式
- 支持组合支付
- 支付完成后订单状态正确变化
- 支付完成后可打印小票

### 26.4 退款验收

- 已支付订单可以发起退款
- 退款金额不能超过可退款金额
- 会员余额支付退款后余额能正确退回
- 退款后订单状态正确变化
- 每次退款都有退款记录
- 无权限人员不能执行退款

### 26.5 财务验收

- 会员充值不直接计入营业收入
- 会员余额消费时计入营业收入
- 系统可按日统计营业收入
- 系统可按支付方式统计收款金额
- 系统可统计退款金额
- 系统可导出财务明细

### 26.6 权限验收

- 不同角色登录后看到不同菜单
- 收银员不能查看平台租户管理
- 发型师只能查看自己的业绩
- 无权限人员不能查看财务报表
- 权限变更后重新登录生效

### 26.7 品牌客制化验收

- 修改租户店名 / Logo 后，管理后台与小票展示同步变化
- 租户 A 与租户 B 可配置不同店名与 Logo，互不影响
- （若有小程序）通过不同入口进入后，展示对应租户的店名、Banner 与联系方式
- 未配置 Logo 时有默认占位，不影响正常使用
- 客制化仅影响展示与配置，不改变收银 / 充值 / 退款业务规则

## 27. 业务风险与注意事项

### 27.1 财务口径风险

会员充值、赠送金额、余额消费、退款之间关系复杂，必须在产品设计中明确口径，避免老板看到的营业额与实际现金流混淆。

### 27.2 数据隔离风险

系统采用 SaaS 模式，不同租户数据隔离是底线要求，任何列表、详情、导出、报表都必须遵守租户隔离规则。前期“不会连锁”不能代替隔离设计——隔离是多店共用同一系统的前提。

### 27.3 退款与余额风险

退款、余额调整、赠送金额扣减等操作容易造成财务差异，必须保留完整流水和操作日志。

### 27.4 门店使用习惯风险

理发店员工信息化水平不一，收银界面必须简单直接，避免过多复杂配置影响日常使用。

### 27.5 客制化范围失控风险

若把“每个店名字不一样、小程序看起来不一样”做成按店改代码，会从 SaaS 退化成项目制。需求与验收必须坚持：**差异走配置，能力走统一产品**。

### 27.6 小程序主体与品牌风险

统一小程序方案下，微信侧小程序名称通常只有一个；各店差异主要体现在进入后的店名、Banner、分享卡片。若商户强要求独立小程序名称 / 独立主体，需走扩展方案并单独评估审核与运维成本。

## 28. 后续待确认问题

### 28.1 业务规则待确认

- 首期是否严格 1 租户 1 门店？（建议：是）
- 会员是否全租户通用，还是只在单门店可用？（单店期二者等价）
- 多门店之间会员余额是否允许跨店消费？（后续）
- 赠送余额消费时是否计入员工提成？
- 消费扣款时优先扣本金还是赠送金额？
- 退款时本金和赠送金额如何退回？
- 会员卡项是否允许转赠？
- 充值活动是否支持叠加优惠券？
- 不同发型师参与同一订单时业绩如何分摊？
- 发型师提成按原价、折后价还是实收金额计算？
- 门店是否需要交班功能？
- 是否需要接入微信/支付宝官方支付？

### 28.2 客制化与小程序待确认

- 会员小程序是否纳入首期范围？
- 首期小程序采用「统一主体 + 租户入口」还是「每店独立小程序」？
- 主题色是否纳入 MVP？
- 品牌配置由平台代配，还是商户老板自助修改？
- 小票是否必须打印 Logo（受打印机能力限制）？
- 是否允许商户自定义小程序首页模块顺序？

## 29. 初步需求文档结构建议（给评审用）

写/改本类 SaaS 初步需求时，建议按下面顺序组织，避免一上来堆功能清单：

1. **定位与边界**：卖给谁、首期不做连锁、后端复用 / 前端可配  
2. **租户模型**：1 租户 1 店、隔离规则、套餐  
3. **品牌客制化**：哪些可配、哪些不可配、小程序策略  
4. **角色与权限**  
5. **核心业务闭环**：会员 → 充值 → 收银 → 退款 → 日结  
6. **扩展业务**：预约、库存、营销（标清优先级）  
7. **报表与财务口径**  
8. **MVP 与暂缓**  
9. **验收标准**  
10. **待确认问题**
