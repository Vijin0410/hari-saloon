# 订单服务人员与助理改动审核

审核日期：2026-11-18。范围：本轮收银人员默认分配、统一分配、已结算订单人员更正及个人记录筛选。

## 审核结论

本轮功能已贯通前端表单、后端校验、订单明细存储、人员更正审计和订单查询。人员归属保存到实际消费明细，具备后续按员工分别关联主服务业绩与助理业绩的数据基础。当前尚未实现正式提成计算和员工提成汇总，不能将订单列表金额或项目排行直接当作应发提成。

## 各处改动的用途

| 改动 | 实际用途 |
| --- | --- |
| 角色开单身份、门店人员选项 | 新增明细带入当前登录用户；明确配置为助理时带入助理栏，候选人员限定租户及门店 |
| 明细服务人员、助理字段 | 分别写入 `salon_order_item.staff_id`、`assistant_id`，通过用户ID归属，姓名仅用于展示 |
| 统一服务人员弹窗 | 确认后回填所有明细，取消保持各自分配；提交仍使用同一套明细字段，不产生第二份人员归属 |
| 结算前校验 | 直接支付和扫码出码前校验主服务人员必填、人员有效、主服务人员与助理不同，挂单可暂存未分配明细 |
| 更正原人员回显 | 逐项回显订单原人员；受控下拉避免异步人员选项替换后丢失选中值；不会套用当前登录用户覆盖历史分配 |
| 更正接口 | 只更新原消费明细的人员字段，保持明细ID、价格、数量、小计不变；明细更新失败会使事务回滚 |
| 更正审计 | 按明细记录前后主服务人员、前后助理的ID及姓名快照、更正原因、操作人和时间 |
| 并发保护 | 订单行锁、完整明细集合及原人员ID校验，防止旧表单覆盖其他人已更正的人员归属 |
| 我的开单、我的服务记录 | 前者按订单创建人筛选，后者按有效明细主服务人员筛选；账号ID由后端读取登录身份，服务记录通过 EXISTS 避免一单重复 |

## 审核中修复的问题

1. 更正表单的下拉框改为受控字段，初次打开、重新打开和异步加载候选人员时均保留原分配。大整数ID按字符串传递，未配置助理保持空值。
2. 原人员停用或离店时仍显示原分配；更正其他人员时允许保留未改变的历史岗位归属。新分配的人员必须属于当前门店的有效候选，不能借此新增停用或其他门店人员。新订单结算继续执行有效人员校验。
3. 统一人员弹窗仅在所有明细分配一致时预选共同人员，不再无条件拿第一条作为整单分配；停用人员不作为整单新分配的默认值。
4. 更正保存检查实际更新行数，防止只产生审计记录却没有更新明细；空明细元素由后端表单校验拒绝。

## 后续提成汇总的接入边界

- 汇总粒度应从消费明细出发，关联订单的租户、门店、支付时间和状态，分别按 `staff_id` 与 `assistant_id` 归属；不能给两个人各累计一次整单金额。
- `create_by` 是开单人，`staff_id` 是主服务人员，`assistant_id` 是助理，三者用途不同。我的服务记录仅匹配主服务人员，助理汇总应单独使用助理ID。
- 后续 P7 需要保存提成规则版本、项目是否参与提成的快照、逐项提成基数、比例、主辅分摊及实际提成金额。当前项目和商品的 `commissionable` 配置不等于已经形成历史提成快照。
- 金额退款目前按订单处理，后续需要明确逐项退款分配和提成回冲口径，不能直接用退款前小计生成应发提成。
- 后续产生已确认或已发放的提成后，更正人员需要联动重算、差额调整或结算锁定；本轮人员审计提供追溯依据，当前并无已发放提成账本可供联动。
- 存量未填写主服务人员的已结算订单，应通过必填原因的更正入口补录，不能按当前操作账号批量推定历史实际服务人员。

## 验证与部署

- 前端回归覆盖原人员回显、大整数ID、空助理、统一回填保留原并发版本、默认登录用户及支付分配。
- 后端 `OrderStaffServiceTest` 覆盖人员必填、主辅不同人、有效门店人员、更正留痕、助理清空、原离店人员保留、旧版本拒绝、明细集合校验及更新失败。
- 数据库集成测试使用 `SALON_TEST_DB_URL`、`SALON_TEST_DB_USER`、`SALON_TEST_DB_PASSWORD` 配置的临时 schema。未配置时跳过，不把单元测试当作数据库事务回滚验证。
- 已有环境需执行 `sql/migrate-order-staff.sql` 后部署后端并重新登录刷新权限；迁移不推定历史订单人员。
