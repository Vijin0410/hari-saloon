# 退款积分与积分功能开关方案

更新时间：2026-11-12。性质：代码现状核对 + 待实施的产品方案；本轮只更新文档，没有修改业务逻辑。

关联：[实施计划](hair-salon-implementation-plan.md)、[前端优化清单](frontend-product-ui-review-2026-11-12.md)、[业务需求](hair-salon-saas-requirements.md)。

## 1. 范围与决定

- **用户已明确：卡项核销暂时不开发。** 不新增扣次、核销支付等链路，不以此阻塞收银、退款、日结和 UI 升级。
- **用户提出：积分应可按店铺选择是否启用。** 本文将其纳入待开发需求，避免不使用积分的门店仍要处理额外字段和操作。
- 退款积分应区分两笔独立权益：**原支付抵扣的积分退回给会员**，以及**该笔消费赠送的积分随退款扣回**。
- 下文的默认值、部分退款算法、积分有效期与不足回收策略均是建议方案，尚未由用户逐项确认，也尚未实现。

## 2. 当前代码核对

| 场景 | 当前行为 | 判断 |
|---|---|---|
| 消费抵扣积分 | 100 分抵 1 元；按批次 FIFO 扣减并保留 sourceLogId | 已实现 |
| 消费赠送积分 | 实收金额 × 会员等级 pointRate，向下取整；写 ORDER 关联流水 | 已实现 |
| 资金全额退款 | apply 判定资金退完时记录抵扣积分退回数量；confirm 写 changeType=9 退回流水 | 已实现基础路径，仍需补边界验收 |
| 部分退款 | 抵扣积分暂不退回；累计资金全退后才退 | 当前实现，不能描述为每次退款都会返积分 |
| 退款扣回消费赠送积分 | 退款确认未执行赠送积分扣回 | 尚未实现，有交易已退但奖励仍保留的缺口 |
| 退回积分的有效期 | changePoints(..., expireTime=null, ...) 写新批次 | 当前没有沿用原有效期，可能把有限期积分变成无到期日 |
| 纯积分支付订单 | 实收资金为 0；当前退款表单要求退款资金至少 0.01 元 | 现有接口无法完成这类退积分，需要独立覆盖 |
| 多笔处理中退款 | apply 按“处理中+成功”资金判断是否全退，但已退积分只汇总成功退款 | 需验证并加强：某笔处理中退款失败时，其他退款不应提前释放全额积分 |
| 店铺积分开关 | 未发现租户级业务开关；仅有积分过期定时任务部署开关 | 尚未实现 |

- `hair-salon-service/src/main/java/com/wangjin/salon/service/service/impl/OrderRefundServiceImpl.java`：`apply` 计算资金及积分退回。
- `hair-salon-service/src/main/java/com/wangjin/salon/service/pay/OrderRefundConfirmExecutor.java`：`confirm` 退回积分和余额，目前没有消费赠送积分扣回。

- `hair-salon-service/src/main/java/com/wangjin/salon/service/model/form/OrderRefundForm.java`：资金退款最小 0.01 元。

## 3. 退款后的目标权益规则

### 3.1 全额退款

- 资金退回原资金渠道或原余额桶；抵扣积分退回积分账户，不折算成额外现金。
- 该订单已赠送积分应扣回，避免全额退款后仍享有消费奖励。
- 两者分开记流水与关联原订单/退款单，即使最终积分净变化为 0，也不能相互抵消掉审计记录。
- 本金/赠送余额退回继续遵循现有先本后赠及原订单扣款上限，不与积分混为一类资产。

示例（建议规则）：某笔应收 100 元，使用 1000 积分抵 10 元，再付 90 元资金，并获赠 90 积分。全额退款应退资金 90 元、退回抵扣积分 1000 分、扣回消费赠送 90 分。不能退 100 元资金后再退 1000 积分。

### 3.2 部分退款（推荐累计比例法，待确认）

当前只支持资金金额级退款，建议第一阶段以原订单实收资金比例分摊权益；按服务/商品行退款仍为后续范围。产品文案应说明输入的是资金退款额，以及同时退回/扣回的积分。

记原订单实收资金为 R，原抵扣积分为 P，原实际赠送积分为 G；累计成功资金退款（含本次确认）为 C。R > 0 时：

- 累计应退抵扣积分 = floor(P × C / R)。
- 累计应回收消费赠送积分 = floor(G × C / R)。
- 本次处理 = 累计应处理数 - 先前成功已处理数。赠送回收的“已处理”需包含已扣、已失效而无需再扣、已记待追回，防止重复回收。
- 最后一笔全额退完时补足所有尾差，数量不超过原订单实际抵扣/赠送积分。不能根据当前等级或当前倍率重新计算 G。

上例先退 45 元资金，即成功退款 50%，建议退回 500 抵扣积分、回收 45 赠送积分；余下 45 元资金退款成功后再处理剩余数量。

该规则属于资金退款额与积分共同组成的权益分摊。后续若增加“按原项目价格退货”或“按支付总价值输入退款”入口，应另建明确的分摊口径，避免前后端混用分母。

纯积分订单 R=0 不能套上述除法，也不能伪造 0.01 元退款。建议先支持有退款权限的全单积分退回，资金额为 0；部分权益退还留到能定位服务/商品行时设计。

### 3.3 成功、处理中、失败与并发

- 发起退款时只占额度并展示预计权益，不能提前增加可用积分。
- 渠道成功确认后才执行退回/扣回；失败或撤销释放占用，不执行成功积分变动。
- 同一订单的资金退款、抵扣积分退回、赠送积分回收共用一致的额度控制；可采用订单级行锁/条件更新，不依靠前端按钮禁用。
- 第一阶段建议同订单同一时间只允许一笔处理中退款，减少已成功、处理中与失败之间的权益分配冲突。
- 重复回调、查询补偿、重试不得重复退积分或重复回收。订单只有在资金和应恢复权益均处理完毕后才能表现为完整退款。

### 3.4 有效期与积分不足

退回抵扣积分应关联原消费扣减批次，建议保留原有效期；原批次已过期时，可配置一个明确的售后宽限期，具体天数待确认。不能无说明地改成永久积分。

消费赠送积分回收还要区分：

| 原赠送积分状态 | 建议处理 |
|---|---|
| 仍在该订单原赠送批次内可用 | 定位该批次回收，写退款扣回流水，避免普通 FIFO 误扣其他来源 |
| 已按有效期过期失效 | 已失效部分无需再次扣除可用积分，但记录冲正归属，避免重复处罚 |
| 已被消费、兑换或转作其他使用 | 不直接把当前积分扣为负数，不因积分不足卡住已成功的渠道退款；回收策略需单独实现 |

对“奖励已用”的推荐方案是记录**待追回积分**：在现有积分余额不为负的前提下，按明确规则抵扣后续新奖励；存在待追回时限制新的积分抵扣，并向管理员展示记录。原抵扣积分的售后退回仍须独立记账，不得被静默吞掉，也不能擅自少退现金。

“待追回”增加数据与运营复杂度，尚未拍板。如果选择更简单的人工处理方案，也必须有明确的权限、原因与记录；该策略应在开发消费赠送回收前确定。历史已送、已用、已过期的奖励不能只靠一次 `changePoints(-G)` 处理。

## 4. 积分功能开关（待开发）

### 4.1 配置粒度与默认建议

- 配置名称：“启用会员积分”。入口建议为“业务配置 → 会员设置”。
- 首期按**租户（当前独立店铺）**配置，不用修改部署 yml，不做全平台统一开关。
- 同租户多门店暂时共用一套积分策略，避免共享会员资产因门店开关不同出现冲突；若以后要门店覆盖，先明确积分账户归属。
- 新租户建议默认关闭，需要时主动开启。存量租户迁移显式保持开启，以保留原行为；不可因配置缺失自动把旧店积分关掉。此处为建议默认值，尚未实施。
- 仅有相应管理权限的用户可更改；保存记录操作者、时间及前后值，并失效配置缓存。前端用服务端返回的能力状态组织页面。
- 功能关闭不等于移除会员等级、余额、充值、折扣或标签。它们仍独立可用。

### 4.2 开关行为矩阵

| 区域 | 开启 | 关闭 |
|---|---|---|
| 会员列表/档案 | 显示积分列、积分资产卡、调整与流水入口 | 隐藏日常积分列、资产卡与普通调整入口；不占空白卡位 |
| 收银 | 显示可用积分与抵扣、完成后的奖励信息 | 隐藏积分相关控件，新订单不赠送、不抵扣 |
| 会员等级 | 显示积分倍率 | 隐藏倍率输入/展示，服务折扣与其他权益继续有效 |
| 小票/订单常规展示 | 按真实记录显示积分 | 新无积分订单不显示积分占位；历史有积分订单保留真实构成 |
| 后端写接口 | 正常校验积分获得、抵扣与调整 | 拒绝新的非零积分抵扣和普通调整，不静默忽略；正常无积分收银继续完成 |
| 消费赠送/充值赠送等新发放入口 | 依规则发放已支持的奖励 | 停止新增发放；未实现的发放场景不因此视为已完成 |
| 历史订单退款 | 按原记录退回/回收积分 | 仍按原记录执行，不能因当前关闭而跳过售后 |
| 历史余额、批次和流水 | 正常保留 | 不清零、不删除；提供管理权限下只读的历史查询入口 |
| 已有积分过期 | 按原规则 | 建议继续原有效期规则并记录流水；关闭不等于暂停期限，需在关闭说明中告知 |

已有积分的店铺关闭时，需要展示未使用积分汇总与处理说明，不新增自动清零或现金兑换动作。对有存量积分的店铺，可先把消费赠送倍率设为 0、保留抵扣，待制定过渡安排后再关闭总开关；新店没有存量积分时关闭可直接保持简洁。暂不为了此场景再堆叠多套营销开关。

`wj.salon.point-expire-enabled` 仅控制过期定时任务，既不能隐藏积分界面，也不能停止送分/抵扣，不能拿来充当店铺积分总开关。

### 4.3 未支付订单与异步确认

- 尚未出码/开始支付的新订单以当前能力状态校验；关闭后不允许新增积分使用。
- 若已有包含积分的扫码待支付单，不能在渠道扣款后仅因开关变化拒绝结算；需在支付开始时保存积分能力与规则快照，并按该快照完成对应确认。也可在安全关闭渠道单后让用户重新确认金额，不能直接删掉抵扣项。
- 原先已发起但尚未确认的支付是否继续按快照赠送，需要在关闭说明中告知；建议保留该笔已开始交易的原规则，后续新交易走关闭状态。
- 切换配置不得重算历史订单、改变历史兑换比例，或清除仍待处理的退款积分。

## 5. 前端与数据落地要求（建议）

- 退款确认区分“资金退回”“抵扣积分退回”“消费赠送积分扣回”，显示本次预计数量和处理状态。
- 在积分关闭后，常规工作区不显示冗余积分组件；历史订单与退款中仅在确实涉及积分时展示历史权益，不能把它们隐藏成无法核对。
- 保留原订单支付时的积分数量、抵扣金额、实际赠送流水与适用规则；退款以原记录计算，不按退款时等级重算。
- 按需补充退款积分冲正字段/记录，区分退回、扣回、已过期无需扣、待追回，并关联批次。已有 9=退款退回只表达正向退回，不能冒充赠送扣回。
- 若采用待追回方案，再增加明确的记录和结清规则；不为尚未确认的策略提前建通用规则引擎。
- 新接口继续遵守 Form/Query 入参、VO 出参、权限、租户隔离、校验、SQL 注释及审计规范；本次文档不承诺未设计的接口已存在。

## 6. 验收清单（待开发时执行）

- [ ] 100 元订单用 1000 积分抵 10 元、支付 90 元并获赠 90 分；全退资金 90 元、返 1000 分、回收 90 分，记录分开且可追溯。
- [ ] 按最终选定部分退款规则，验证多次小额退款、尾差补足、累计不超原抵扣/奖励数量。
- [ ] 纯积分订单退积分不产生虚假资金退款；不发生除零。
- [ ] 已过期奖励不重复扣可用积分；已使用奖励按选定策略处理，不用现有不足校验阻断已成功的渠道退款。
- [ ] 原抵扣积分退回后有效期按确认规则执行，无意外永久化。
- [ ] 处理中退款不提前增加可用积分；渠道失败、重复回调、查询补偿不造成重复或提前退回。
- [ ] 同订单并发退款的资金与积分额度一致；一笔失败不会影响其他成功退款的应退权益。
- [ ] 积分关闭：会员、等级、收银页面不出现日常积分冗余；直接调接口也不能新增积分业务。
- [ ] 关闭期间旧订单仍能退款、追溯流水；重新开启能正确读取保留的余额与历史。
- [ ] 已有扫码待支付单遇配置切换，渠道确认可按原交易快照正确完成；未支付新订单使用当前设置。
- [ ] 新租户、存量租户默认迁移和不同租户开关互不影响；配置权限及缓存刷新有效。

## 7. 建议实施顺序与待确认项

1. 先确认积分回收与部分退款规则，修复赠送积分未扣回等一致性缺口。
2. 实现租户级积分开关及旧店迁移，前后端联动简化界面，同时覆盖历史售后与异步支付。
3. 将退款积分预览、流水和开关状态纳入会员/收银 UI 优化。
4. 卡项核销继续暂缓；不将积分可选化扩展为新的卡项开发任务。

实施前仍需确认：部分退款累计比例是否采用、原批次到期后的售后宽限、奖励已使用时采用待追回还是人工处理、新租户默认值及存量店铺停用过渡。当前需求方向已记录，无需为更新文档先行阻塞。
